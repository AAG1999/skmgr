# How It Works

`skmgr` is non-destructive and avoids file duplication.

1. **Resolution:** Skills are fetched and cached in `~/.skmgr/cache/`.
2. **Installation:** Skills are staged, then renamed into the canonical `.agents/skills/` directory, so a failure never leaves a half-installed skill.
3. **Linking:** Symlinks are created from agent-specific directories (e.g. `.cursor/skills/my-skill`) back to `.agents/`.

Links are **relative**, so moving or renaming the project — or mounting it at a different path inside a container — does not break them. Links left absolute by an older `skmgr` are rewritten on the next sync.

Run `skmgr tree` to see the resulting layout, or `skmgr doctor` to check that this machine can do all of the above.

For system design diagrams, see [architecture.md](architecture.md) and [flow.md](flow.md).

## Caching and refs

A repository is cloned into `~/.skmgr/cache/git/<hash-of-source>/` once and reused. Each commit used is extracted under `commits/<sha>/` and never modified afterwards.

On every subsequent run `skmgr` fetches from the remote, then decides which commit to use:

- **A branch** (or no `ref`) follows the remote.
- **A tag or commit SHA** is immutable, so once cached the network is skipped.

Transient network failures are retried three times with exponential backoff.

```bash
skmgr cache info                     # what is in there, and how big
skmgr cache prune --older-than 30d   # drop trees unused for a month
skmgr cache prune --max-size 2GB     # evict least-recently-used until it fits
```

`skmgr clean --cache` wipes the whole cache.

> **Upgrading:** versions before the per-commit cache stored one checkout per repository. Those entries cannot be read by the current layout, so the first run after upgrading deletes them. The next install re-fetches what it needs.

## Crash safety

Every file `skmgr` owns — the manifest, lockfile, global ledger, managed `.gitignore` blocks, and merged rule files — is written to a temporary file and renamed into place. If the process dies mid-write you are left with the old file or the new one, never a truncated one.

## File permissions and ownership

Installed files keep the permission bits they had in the source. Ownership is not copied — files are owned by whoever ran `skmgr`. Symlinks inside a skill are recreated as symlinks; one pointing outside the skill aborts the install.

## `.gitignore` management

When `skmgr` creates symlinks in `.cursor/` or `.claude/`, it adds ignore rules wrapped in a managed block:

```gitignore
# skmgr:managed
# Generated by skmgr. Do not edit inside this block; changes are overwritten.
.cursor/skills/frontend-design
# skmgr:end
```

The block is regenerated on every run. Keep your own rules outside the markers. Unbalanced markers cause `skmgr` to refuse to touch the file.

## Orphan & broken link cleanup

When skills are removed from `skmgr.yml`, or auto-discovery changes the skill list, `skmgr` cleans the canonical `.agents/` directory and prunes broken symlinks from agent target directories. For merged rules, it diffs the previous lockfile against the new manifest and removes managed blocks for anything dropped.

## Installing the CLI

How to get the `skmgr` binary itself is covered in the [README](../README.md#install). Short version:

| Platform | One-liner |
|----------|-----------|
| Linux / macOS | `curl -fsSL …/scripts/install.sh \| sh` |
| Windows (PowerShell) | `irm …/scripts/install.ps1 \| iex` |

The Windows script installs to `%LOCALAPPDATA%\skmgr` and adds that folder to your user `PATH`. After that, `skmgr self-update` can keep the binary current.

## Windows

`skmgr` prefers real symlinks. When that permission is missing it falls back, in order:

1. **A directory junction** (`mklink /J`) — usual outcome; installs work normally.
2. **A copy** — refreshed on each `skmgr sync`, with a warning at install time.

Only a permission failure triggers the fallback. Run `skmgr doctor` to see which mode you are in.

Skill names that differ only in case are rejected at parse time, because they collide on Windows and macOS filesystems.

## Global scope

`scope: global` installs to `~/.agents/` and links into agent directories under your home (`~/.cursor/skills/`, `~/.claude/`, `~/.github/`, `~/.gemini/config/`). It never writes into the project you happen to be standing in.

Because `~/.agents/` is shared, `skmgr` records which project owns which global skill in `~/.skmgr/global.lock` and only prunes a global skill once no project claims it. Remove unclaimed globals with `skmgr clean --global`.

## CI usage

```yaml
- name: Install Agent Skills
  run: skmgr install --frozen

- name: Verify Agent Skills
  run: skmgr verify
```

Cache downloads between runs:

```yaml
- uses: actions/cache@v4
  with:
    path: ~/.skmgr/cache
    key: skmgr-${{ hashFiles('skmgr.lock') }}
```

Add `SKMGR_OFFLINE=1` if the job must not reach the network. To fail a PR only on skill drift (exit code `3`), see [exit-codes.md](reference/exit-codes.md).

For private repositories, set `GIT_TERMINAL_PROMPT=0` so a missing credential fails instead of hanging. See [private-git.md](reference/private-git.md).
